TO-CLARIFY: open items for mva-ext-dtso/ and drivers/dma/fpga-sampler-dma.c
=============================================================================

This file has two sections:
  - "Device tree" - open items about mva-ext-dtso/iio-mem-access-overlay.dtso
  - "DMA-engine provider" - open items about the register writes and
    device-tree consumption added to drivers/dma/fpga-sampler-dma.c

===============================================================================
SECTION: Device tree
===============================================================================

The overlay in mva-ext-dtso/ was drafted from existing repo sources
(mem-access-overlay.dtso, drivers/iio/adc/dma-sampler.c, and
dma-devicetree-design.txt / TODO-spi-offload.txt), but several details
could not be confirmed from those sources alone. Please verify the
following before using this overlay for real hardware bring-up:

1. LSRAM aperture address/size (reg "lsram", 0x80000000 / 0x24000)
   -----------------------------------------------------------------
   Derived from dma-sampler.c's compile-time constants:
     DMA_SOURCE_ADDRESS       = 0x80000000
     SAMPLER_LSRAM_WORD_COUNT = 18432
     SAMPLER_SAMPLES_PER_LSRAM_WORD = 4
     SAMPLER_BUFFER_BYTE_COUNT = 18432 * 4 * 2 = 0x24000 bytes
   These are driver-side constants matched against a specific FPGA
   gateware build; I could not find an authoritative FPGA-side address
   map (e.g. a gateware register/memory-map document) confirming this
   is the LSRAM's actual bus address as seen by the DMA controller, or
   that it is stable across gateware revisions. Please confirm with the
   FPGA design team, or point me at the gateware memory map if one
   exists in ../a2d/beagleVFire/sources/FPGA-design.

2. #dma-cells value (chosen: 0)
   -----------------------------
   Chose 0 cells (no per-request parameters) because the FPGA DMA IP
   appears to expose exactly one, fixed-function channel with no
   selectable modes/indices anywhere in dma-sampler.c or the UIO tool.
   If a future/actual gateware revision exposes multiple channels or a
   channel-select/flags parameter, this should become
   `#dma-cells = <1>` (or more) and the `dmas = <&fpgadma>;` reference
   in the sampler node would need an extra cell, e.g.
   `dmas = <&fpgadma 0>;`.

3. Clocks / resets for the DMA controller and sampler nodes
   ---------------------------------------------------------
   No `clocks`/`clock-names`/`resets` properties were added because none
   were found referenced in dma-sampler.c, the UIO overlay, or the
   uio-adc-sampler-control tool. If the FPGA fabric-bus infrastructure
   actually requires the kernel to explicitly enable a fabric clock (or
   deassert a reset) for these IP blocks to function, that is currently
   handled outside of Linux (e.g. always-on fabric clock, or set up by
   firmware/HSS before Linux boots) - please confirm this assumption
   holds, or supply the correct clock/reset bindings if not.

4. [RESOLVED] `reg-names`/multi-window binding for the sampler node
   -------------------------------------------------------
   An earlier revision of this overlay split the sampler's `reg` into
   two named windows ("ctrl" + "lsram"), a binding introduced to match
   how dma-sampler.c internally treats SAMPLER_ADDRESS and
   DMA_SOURCE_ADDRESS as separate apertures of the same logical block.
   This has since been resolved by item 7 below: LSRAM is now described
   by its own standalone devicetree node (not a second reg window on the
   sampler node at all), so the sampler node's `reg` is back to a single,
   unnamed window (just "ctrl") and `reg-names` has been dropped
   entirely. See item 7 and item 5 (now also resolved) for the final
   design.

5. [RESOLVED] Whether the "lsram" reg window should live on the sampler
   node at all
   -----------------------------------------------------------------------
   Resolved as part of item 7 below: LSRAM is described by its own
   standalone node (no "compatible", reg-only), referenced directly by
   the DMA-engine provider node (fpgadma) via a new "rohm,lsram" phandle
   property - NOT by the sampler node at all. This is a cleaner
   resolution than either original alternative (keeping it on the
   sampler node, or duplicating it directly onto fpgadma as a second reg
   window): it correctly models LSRAM as its own hardware entity (not
   owned by either the sampler or the DMA controller), is referenced by
   whichever driver actually needs it (today, only
   drivers/dma/fpga-sampler-dma.c), and sidesteps the fabric-bus
   "ranges" gap (see item 7) without forcing the sampler node itself out
   of fabric-bus@40000000.

6. reg/interrupt numbers themselves (0x60000000/0x60010000/0x80000000,
   IRQ 121/122)
   -----------------------------------------------------------------------
   Copied verbatim from mem-access-overlay.dtso and dma-sampler.c; these
   are almost certainly correct for the current gateware build actually
   in use, but were not independently re-derived/verified against a
   gateware build artifact in this pass.

7. [RESOLVED] fabric-bus@40000000 "ranges" does not cover the LSRAM
   aperture (0x80000000) - LSRAM split into its own standalone node
   -----------------------------------------------------------------
   Symptom reported after first real hardware test: dma-sampler-dmaengine
   probed (once its "compatible" was corrected to match fpgasampler's
   "rohm,fpga-adc-sampler"), but then stayed stuck with
   "platform 60000000.sampler: deferred probe pending: sampler-dmaengine:
   failed to request dma channel" forever, and no /sys/bus/iio/devices/
   entry ever appeared.

   Root cause: the overlay originally nested fpgadma/fpgasampler as
   children of "fabric-bus@40000000" (mirroring mem-access-overlay.dtso's
   UIO nodes), with LSRAM described as a second, named "lsram" reg
   window on the sampler node. That bus's "ranges" property - defined
   identically in ALL FOUR board .dtsi variants checked
   (mpfs-beaglev-fire-fabric.dtsi, mpfs-disco-kit-fabric.dtsi,
   mpfs-icicle-kit-fabric.dtsi, mpfs-video-kit-fabric.dtsi) - is:

       ranges = <0x0 0x40000000 0x0 0x40000000 0x0 0x20000000>, /* FIC3-FAB */
                <0x0 0x60000000 0x0 0x60000000 0x0 0x20000000>, /* FIC0, LO */
                <0x0 0xe0000000 0x0 0xe0000000 0x0 0x20000000>, /* FIC1, LO */
                <0x20 0x0 0x20 0x0 0x10 0x0>, /* FIC0,HI */
                <0x30 0x0 0x30 0x0 0x10 0x0>; /* FIC1,HI */

   The "FIC0, LO" window is exactly 0x60000000 + 0x20000000 =
   0x80000000 wide, i.e. it covers [0x60000000, 0x7fffffff] INCLUSIVE
   and stops ONE BYTE before the LSRAM window's start address
   (0x80000000). The "lsram" reg entry on fpgasampler
   (<0x0 0x80000000 0x0 0x24000>) therefore had NO matching "ranges"
   entry to translate through. fpga_sampler_dma_of_get_lsram()'s call
   to of_address_to_resource() on that reg entry failed as a result
   (translation error, not a transient/deferred condition), which made
   fpga_sampler_dma_probe() return a hard error and RETURN WITHOUT EVER
   CALLING of_dma_controller_register(). Since the DMA provider's
   of_dma controller was consequently never registered for fpgadma's
   of_node, dma-sampler-dmaengine's dma_request_chan(dev, "rx") kept
   getting -EPROBE_DEFER indefinitely (the provider node exists and is
   "okay", but of_dma_find_controller() never finds a matching
   registration for it) - matching the exact symptom reported.

   Fix applied (final): LSRAM is now described by its own small,
   standalone devicetree node - "lsram: lsram@80000000 { reg = <0x0
   0x80000000 0x0 0x24000>; };" - placed as a DIRECT child of the root
   node ("&{/}"), NOT nested inside fabric-bus@40000000. It has no
   "compatible" property, so of_platform_populate() never turns it into
   a platform_device (strict mode skips compatible-less nodes) - it
   exists purely as a devicetree-level resource locator. At the root,
   its `reg` is a raw CPU-physical address with NO bus translation step
   at all, so of_address_to_resource() now succeeds unconditionally,
   matching what dma-sampler.c's existing devm_ioremap(0x80000000, ...)
   call already implicitly assumed (a direct 1:1 physical mapping, no
   translation). fpgadma (the DMA-engine provider node) references it
   directly via a new "rohm,lsram = <&lsram>;" phandle property (see
   DMA-engine provider section item 3, also updated).

   Crucially, splitting out ONLY the LSRAM node (rather than moving the
   whole fpgadma/fpgasampler pair to root, as a prior revision of this
   fix did) lets fpgadma and fpgasampler go back to being children of
   fabric-bus@40000000, which is where they topologically belong - they
   are genuine FPGA-fabric IP blocks reachable through the exact same
   FIC0 decode window as any other fabric-bus sibling (e.g.
   cape_gpios_p8/p9, hsi_gpios), and their own remaining reg windows
   (0x60000000/0x60010000) translate through fabric-bus's "ranges" just
   fine - it was only the LSRAM address specifically that fell outside
   the declared ranges. The codebase also does not strictly enforce
   "fabric IP must be nested under fabric-bus" even when it would
   translate correctly (e.g. mailbox@50000000 in
   mpfs-beaglev-fire-fabric.dtsi sits directly under root despite its
   address falling inside fabric-bus's declared ranges), so placing just
   the LSRAM node at root is consistent with existing conventions, not a
   novel exception.

   Alternatives considered but NOT applied (recorded in case this
   decision needs revisiting):
     a) Extend fabric-bus@40000000's "ranges" (via a separate
        "&{/fabric-bus@40000000} { ranges = <...>; };" overlay
        fragment, since dtc overlays replace a targeted property
        wholesale - the full existing list would need repeating plus a
        new <0x0 0x80000000 0x0 0x80000000 0x0 0x20000000> entry) to
        explicitly cover the LSRAM window. Not applied because it
        requires asserting a specific physical/SoC-FIC-decode-window
        fact (that 0x80000000 really is part of an existing FIC0
        non-cached alias window, as opposed to some other, unrelated
        address range that only numerically happens to equal
        0x80000000) that could not be independently verified against
        an authoritative Microchip PolarFire SoC memory map document in
        this pass - please confirm with the FPGA/hardware team if this
        approach is preferred over the standalone-node restructuring
        actually applied.
     b) Keep LSRAM addressing on the sampler node (or fpgadma), but have
        fpga_sampler_dma_of_get_lsram() read the LSRAM address/size via
        plain (non-"reg") vendor properties (e.g.
        "rohm,lsram-addr"/"rohm,lsram-size" parsed with
        of_property_read_u64()) instead of "reg", since plain integer
        properties are never translated through bus "ranges". Not
        applied because it would depart further from standard "reg"
        devicetree conventions than necessary, when a standalone node
        (which keeps the idiomatic `reg`-based address description,
        just placed where it translates correctly) achieves the same
        correctness with less novelty.
     c) Move the whole fpgadma/fpgasampler pair to root (the first fix
        attempted). Superseded by the current, more surgical fix: only
        LSRAM - the actual node whose address falls outside
        fabric-bus's ranges - needs to live at root; fpgadma/fpgasampler
        have no such problem and are better left as fabric-bus children,
        matching their real topology.

None of the above block using this overlay for early bring-up/experiments
(the values used are the best available from existing sources), but they
should be confirmed - especially items 1-2 and 7 - before relying on this
overlay for anything beyond initial driver development.

SECTION: DMA-engine provider (drivers/dma/fpga-sampler-dma.c)
===============================================================================

The skeleton driver was filled in with real register writes (mirrored
from dma-sampler.c's dma_sampler_start_transfer()/dma_sampler_irq_handler())
and now obtains its register window and LSRAM source address/size from
device tree instead of hard-coded constants. This introduced several new
design decisions / assumptions that need confirmation:

1. No hardware "half ready" polling before starting a transfer
   -----------------------------------------------------------------
   dma_sampler_start_transfer() in dma-sampler.c busy-waits on
   dma_sampler_buffer_is_ready() (SAMPLER_STATUS_REG bits 5/6) before
   programming each DMA transfer. fpga_sampler_dma_start_transfer() in the
   new driver does NOT do this, because that status register lives in
   the *sampler* device's MMIO window (0x60000000), which this DMA
   driver has no handle to (only the sampler driver maps it). As written,
   the new driver will kick off a transfer immediately when a period
   completes/is issued, without checking that the FPGA has actually
   finished writing that LSRAM half - this could read stale or
   in-progress data if the ADC/SPI side is slower than assumed.
   Two possible fixes, need a decision:
     a) Also map SAMPLER_STATUS_REG in this DMA driver (would need a
        second phandle/reg reference to the sampler's "ctrl" window, or
        a small register-level API exposed by the sampler driver), or
     b) Make the readiness signal an explicit hardware trigger (e.g. via
        the planned SPI-offload trigger mechanism - see
        TODO-spi-offload.txt) so the DMA driver is only ever kicked once
        the sampler side is already known-ready, rather than the DMA
        driver polling a status register itself.
   Not resolved in this pass - flagged as the most important open item.

2. Transfer/abort semantics for terminate_all()
   -----------------------------------------------------------------
   No documented hardware bit was found for "abort an in-flight DMA
   descriptor" (dma-sampler.c never needed one, since it never
   implemented dmaengine's terminate_all() concept - its abort() just
   walks its own driver-private block list). fpga_sampler_dma_terminate_all()
   currently only masks the completion interrupt and drops the software
   descriptor pointer; an already-started hardware transfer will still
   run to completion in silence. If the DMA IP has an actual "cancel/
   reset" register/bit, please point it out so terminate_all() can use
   it for a cleaner, faster abort.

3. [RESOLVED] `rohm,lsram` phandle property (new, driver-specific)
   -----------------------------------------------------------------
   An earlier revision added a custom devicetree property on `fpgadma`,
   `rohm,sampler = <&fpgasampler>;`, so fpga_sampler_dma_of_get_lsram()
   could find the sampler node and read its "lsram"-named reg entry.
   This created an unusual cross-reference in the opposite direction of
   the normal `dmas`/`dma-names` consumer->provider link.

   Resolved together with device-tree section item 7: LSRAM is now its
   own standalone devicetree node (no "compatible", reg-only), and
   `fpgadma` references it directly via a new `rohm,lsram = <&lsram>;`
   phandle property instead. This is still a custom, driver-specific
   property (not part of any generic/upstream dmaengine binding), but
   it no longer back-references the sampler node at all - `fpgadma` now
   points at a small, independent resource descriptor that describes
   exactly the one thing this DMA driver actually needs (the LSRAM
   aperture), rather than reaching into a sibling consumer device's
   node. This is a materially more conventional shape for a phandle
   property. No further action needed unless this binding is ever
   upstreamed/formally documented (would still need a
   Documentation/devicetree/bindings/dma/rohm,fpga-sampler-dma.yaml
   schema, as before).

4. `#dma-cells = <0>` and of_dma_simple_xlate() assumption
   -----------------------------------------------------------------
   probe() registers via of_dma_controller_register() using the generic
   of_dma_simple_xlate() helper, which is only correct for `#dma-cells =
   <0>` (as currently declared in the overlay). If the DT design changes
   to `#dma-cells = <1>` per TO-CLARIFY.txt item 2 (device-tree section),
   this xlate function and the "dmas = <&fpgadma>;" consumer property
   would both need to change together.

5. Byte counts/addresses assumed to fit in 32 bits
   -----------------------------------------------------------------
   DMA_DESC_0_SOURCE_ADDR_REG/DEST_ADDR_REG/BYTE_COUNT_REG are all
   written with plain 32-bit iowrite32() calls (matching dma-sampler.c's
   existing use of `u32 src, dst`), using lower_32_bits() to truncate the
   dma_addr_t/resource_size_t values obtained from device tree. This
   preserves today's behavior but assumes the DMA IP genuinely only
   supports 32-bit addressing (true today given DMA_SOURCE_ADDRESS/
   DMA_DESTINATION_OFFSET are within the low 4GB) - if the DDR target
   region or LSRAM address ever moves above 4GB, this driver (and
   dma-sampler.c before it) would silently truncate addresses.

6. This driver has not been compiled or tested
   -----------------------------------------------------------------
   Per the environment constraints for this session, none of this code
   has been build-tested. Please compile it against the actual kernel
   tree on the build host and fix any API mismatches (e.g. exact
   devm_platform_ioremap_resource()/of_address_to_resource()/
   of_property_match_string() signatures for the 6.12-based microchip
   kernel) before relying on it.

DMA-sampler-dmaengine IIO driver (drivers/iio/adc/dma-sampler-dmaengine.c)
===========================================================================

This is the NEW, plain-dmaengine-consumer IIO driver, parallel to (not a
replacement for) dma-sampler.c, requesting a channel from
fpga-sampler-dma.c via dma_request_chan() instead of poking FPGA DMA
registers itself. It shares most open items with fpga-sampler-dma.c
above (untested, "half ready" signalling, 32-bit address truncation,
first-sample-discard) plus the following, specific to this file:

7. Bypasses the generic industrialio-buffer-dmaengine.c helper
   -----------------------------------------------------------------
   include/linux/iio/buffer-dmaengine.h + drivers/iio/buffer/
   industrialio-buffer-dmaengine.c is the "standard" way an IIO driver
   is expected to consume a dmaengine channel, but it only drives
   providers that implement device_prep_slave_sg()/
   device_prep_peripheral_dma_vec() (one-shot, per-block descriptors).
   fpga-sampler-dma.c deliberately only implements DMA_CYCLIC, matching
   the FPGA's free-running ping-pong hardware, so that generic helper
   cannot be used here. This driver instead submits ONE persistent
   dmaengine_prep_dma_cyclic() descriptor spanning the whole ping-pong
   buffer in ->postenable, and demultiplexes samples out of it manually
   in the per-period callback. This is a deliberate, but non-standard,
   design choice - please confirm it is acceptable, or consider instead
   extending fpga-sampler-dma.c with a device_prep_slave_sg()-style
   one-shot mode so the generic helper (and its associated mmap/
   zero-copy DMA buffer support) could be used instead.

8. kfifo buffer + per-sample iio_push_to_buffers() vs. DMA-buffer/mmap
   -----------------------------------------------------------------
   Because the generic dmaengine IIO buffer helper isn't used (see item
   7), this driver falls back to a plain software kfifo buffer
   (devm_iio_kfifo_buffer_setup()) and pushes samples one at a time via
   iio_push_to_buffers() from the DMA completion callback
   (fpga_sampler_dmaengine_period_done()). This works but reintroduces
   a per-sample copy that a "real" DMA-mapped/mmap'd IIO buffer (as
   dma-sampler.c already provides via iio_dma_buffer_*) would avoid.
   At the target sample rates (up to 1 Msps) this copy overhead should
   be measured/benchmarked before deciding this is an acceptable
   trade-off for production use.

9. dma_alloc_coherent() ping-pong buffer allocated/freed every
   buffer enable/disable cycle
   -----------------------------------------------------------------
   fpga_sampler_dmaengine_postenable()/predisable() allocate and free
   the coherent DMA buffer on every buffer enable/disable, unlike
   dma-sampler.c (which reuses pre-allocated iio_dma_buffer_block
   objects across enable/disable cycles). This is simpler but means
   repeated buffer enable/disable cycles will repeatedly hit
   dma_alloc_coherent()/dma_free_coherent(), which may be slower and is
   more prone to fragmentation-related allocation failures than a
   buffer allocated once at probe() time. Consider moving the
   allocation to probe()/remove() if this driver is taken further.

10. No verification that dma_chan capacity/geometry matches at
    channel-request time
   -----------------------------------------------------------------
   dma_request_chan(dev, "rx") only checks that a channel exists by
   name; whether fpga-sampler-dma.c's device_prep_dma_cyclic() actually
   accepts SAMPLER_BUFFER_BYTE_COUNT/_HALF as buf_len/period_len is only
   discovered later, in fpga_sampler_dmaengine_postenable(), when
   dmaengine_prep_dma_cyclic() returns NULL on mismatch. This driver
   treats that as -EIO without a more specific/actionable error message;
   consider surfacing dmac->lsram_size (or similar) through a capability
   query if this becomes a debugging pain point.
